## 2、摘要

本作品把一块没有网卡、没有桌面系统的黄山派开发板（SiFli SF32LB52），改造成**能听、会说、会主动干活**的语音 Agent。

用户喊一声「你好，openvela」即可下命令，设备执行后把中文结果直接显示在圆屏上；不喊它的时候，它会**按计划自己醒来巡检设备状态并主动汇报**——这正是赛题「能主动、会执行」的要求。

技术上有三个硬骨头：**①** 板载无 WiFi，我们用一根 USB 线同时承载控制台与 PPP 网络链路，把可用带宽压到 12.7 KB/s 后仍跑通了完整闭环；**②** 板载 MEMS 麦克风在 openvela 全树**没有任何可用驱动**，我们实现了 AUDCODEC ADC 采集驱动，并以 5801 Hz μ-law 单字节编码把音频压到 5.8 KB/s 上行（实测交付率 95%，基本零丢样）；**③** 设备端无 ASR 能力，我们把识别放在 PC 侧离线完成（sherpa-onnx Paraformer），设备只做采集与执行。

开发过程中定位并修复了 **23 处 openvela 平台缺陷**与 5 处配置问题，其中 16 处已包含在提交的三个上游补丁内，并已按赛事要求向对应公共仓提交 PR。作品同时沉淀了 2 个自定义 Skill。

## 3、正文

### 3.1 绪论

#### 项目背景与问题定义

嵌入式 AI 演示长期存在两个极端：要么「连着电脑敲命令」，要么「必须联网才有反应」。前者不像产品，后者在展会、教学等网络不可靠的场景下直接失效。

更深一层的问题是**多数演示设备并不会主动做事**——它们只在被问到时才回答。而真实场景里，用户需要的是「设备自己发现问题并告诉人」，比如无人值守时的自检与告警。

我们把问题定义为：**在一块没有网卡、没有操作系统的裸机上，用一根线实现「喊一声就能下命令 + 无人时自己干活」的完整 Agent 闭环，且断网可降级、演示不中断。**

#### 技术难点

1. **无网卡设备的联网**：板载无 WiFi、无以太网。唯一可用的是 USB 串口（CH340）。要在它之上建立 IP 通路，只能走 PPP，而 PPP 的可用带宽实测仅约 12.7 KB/s。
2. **音频上行必须极度压缩**：16 kHz × 16 bit 音频需要 32 KB/s，是可用带宽的 2.5 倍。必须在保证可识别率的前提下把音频压到带宽预算之内。
3. **板载麦克风没有驱动**：openvela 全树没有可用的 SF32LB52 AUDCODEC 录音驱动，HAL 层还有多处调用点被注释、函数无声明、实现被 `#if 0` 屏蔽。
4. **设备端无 ASR**：板子自身没有语音识别能力，本板语音通道依赖的 `/dev/audio/pcm0c` 在 NuttX 下没有音频驱动。
5. **屏幕上的中文**：openvela 自带字体不含 CJK 字形，界面上一个汉字都显示不出来。

#### 创新点

| 层面 | 内容 |
|---|---|
| **交互** | 唤醒词采用赛题统一规定的「你好，openvela」；同时提供屏幕 PTT 按钮作为兜底——**两条入口互不依赖**，任一路径失效演示仍可继续 |
| **技术** | 把「设备采集 → PC 识别 → 云端推理 → 设备执行 → 屏幕回执」拆成端云协同，**设备完全不碰 TLS**，规避了板载 TLS 在 16 KB 以上不可靠的问题，同时让真实 API Key 永不进入设备 |
| **场景** | 主动巡检不是「定时弹个通知」，而是**定时唤醒 Agent 本体**去执行完整工具链并汇报——与被动问答有本质区别 |
| **工程** | 开发中发现并定位了一处 **NuttX 内核信号量竞态**，把设备偶发挂死从「不明原因」缩小到 `sem_waitirq.c:137` 的具体断言与触发路径（详见 3.5 与 3.7） |

### 3.2 系统方案设计

#### 系统总体架构

```
┌──────────────── 黄山派 SF32LB52（设备端，openvela）────────────────┐
│  MEMS MIC → AUDCODEC ADC → μ-law 编码 → WS 二进制帧                 │
│  LVGL 聊天界面（中文，内置 GB2312 字体）                             │
│       ↑ 消息总线 ← agent 核心（工具循环 / 上下文构建 / 技能加载）      │
│  主动任务（cron）→ 到点唤醒 agent → 执行工具链 → 上屏 + 上行          │
└───────────────────────────┬──────────────────────────────────────┘
                            │ PPP over 串口（实测 12.7 KB/s）
┌───────────────────────────┴──────────────────────────────────────┐
│                  PC（云侧，WSL2 Ubuntu）                            │
│  串口桥 bridge.py（独占 CH340，避免打开串口导致板子复位）             │
│  PPP 服务端 pppd + NAT                                             │
│  语音桥 voice_bridge.py：
│      VAD 切句 → sherpa-onnx Paraformer 离线识别 → 唤醒词门控          │
│      → 命令路由 → 回传设备                                          │
│  LLM 代理 llm_proxy.py：设备明文 HTTP → HTTPS（DeepSeek）           │
│      带 --fallback-mock：断网自动降级到本地剧本，演示不中断           │
└──────────────────────────────────────────────────────────────────┘
```

#### 方案论证与选型

| 决策点 | 备选 | 选择与理由 |
|---|---|---|
| **开发板** | 各类 AI 开发板 | **黄山派 SF32LB52**：本届大赛官方专项适配的竞赛板，板载 AMOLED 圆屏 + MEMS 麦克风 + 蓝牙 5.3，可穿戴场景适配度高、技术风险最低 |
| **联网路径** | ① 板载蓝牙 ② USB CDC-ECM ③ PPP over 串口 | **选 ③**：蓝牙无 IP 通路且音频带宽不足；CDC-ECM 需要额外配置且与调试串口冲突。PPP 复用已有的一根 USB 线，是**零额外硬件成本**的方案 |
| **音频编码** | ① 16 kHz PCM ② 8 kHz μ-law ③ 5.8 kHz μ-law | **选 ③**：32 KB/s 根本传不动；8 KB/s 逼近链路上限无余量。5801 Hz μ-law 单字节/样本 = 5.8 KB/s，留出 55% 余量 |
| **LLM 部署** | ① 设备直连 ② PC 代理 | **选 ②**：设备 TLS 在 16 KB 以上实测不可靠（间歇性握手失败并触发断言）。PC 代理同时带来断网降级能力与密钥隔离 |
| **语音识别** | ① 设备端 ② PC 端离线 | **选 ②**：设备端无可用音频驱动；PC 端 sherpa-onnx Paraformer 离线运行，无需联网 |

#### 关键模块设计

**① 端云职责划分**

| 职责 | 设备端 | PC 端 |
|---|---|---|
| 音频采集与压缩 | ✅ | |
| 语音识别 | | ✅（离线） |
| 意图理解 / 工具编排 | | ✅（LLM） |
| 命令执行（shell / 定时任务 / 屏幕） | ✅ | |
| 界面呈现 | ✅ | |
| 断网降级 | | ✅（本地剧本） |

**② 断网 / 弱网降级策略**：`llm_proxy.py` 以 `--fallback-mock` 启动，外部 API 不可达时**自动**切换到本地剧本模型，设备侧无感知。设备与 PC 之间的 PPP 链路走的是本地串口，**不依赖互联网**——所以断网时语音识别、命令执行、屏幕显示全部照常，只有「理解」环节降级。

**③ 主动能力实现**：使用 openvela 的 cron 定时服务，任务属性设 `wake_agent=true`。到点时它**唤醒 agent 本体**并注入一条指令，agent 走完整工具循环（`run_shell` 取 `free`/`ps`/`df`/`uptime`），把结果按 `device-guardian` 技能规定的格式输出并推送上屏。

### 3.3 核心算法与技术原理

#### AI 算法实现

| 环节 | 方案 | 资源占用 |
|---|---|---|
| **语音识别（端侧协同）** | sherpa-onnx Paraformer 中文离线模型，跑在 PC 侧。设备仅上传 5.8 KB/s 的 μ-law 流 | 设备侧零算力；PC 侧单次解码 0.02~0.03 s |
| **重采样** | 设备采样率 5801 Hz 为质数，与 16 kHz 互质。**不做自研重采样**，直接交给 sherpa-onnx 内部 C++ 多相滤波 | 规避了自研有理重采样在互质比下 16000 倍上采样导致的内存爆炸 |
| **意图理解（云端）** | DeepSeek（`deepseek-flash`）经 PC 代理调用，支持工具调用。设备侧发送的请求体经工具裁剪后为 7.3 KB（原 15.5 KB） | 单次巡检约 16 s |
| **唤醒词** | 「你好，openvela」（赛题统一规定）。**匹配规则见下** | 纯 PC 侧，无额外算力 |

**唤醒词匹配的工程取舍**：设备采样率 5801 Hz，奈奎斯特上限约 2.9 kHz，而 `openvela` 中 /v/、/l/ 的辨识特征位于更高频段——**在采样那一刻就已丢失**。实测四次尝试得到四个不同转写（`open renline` / `open rula` / `ok v 乐` / `oppo via`），**没有一次能匹配整串品牌名**；而「你好」四次全对。

因此匹配规则为：**归一化后必须以「你好」开头，且其后至少含一个拉丁字母**。这条规则既接受全部实测变体，又能拒绝「你好，介绍一下你自己」这类正常语句与环境噪声（实测 16/16 用例通过，见 `tools/host/wake_test.py`）。

#### openvela 系统能力的深度运用

本作品**同时落地了「图形」与「AI」两项核心能力**，并深度使用了多媒体子系统：

| 能力 | 使用的 openvela 组件 | 本作品的运用与拓展 |
|---|---|---|
| **图形** | LVGL（openvela 自带图形栈） | 自建 LVGL 宿主与事件循环，实现圆屏中文聊天界面；**发现并修复** `AGENT_LVGL_UI_STACK` 宏定义了却从未被引用、线程实际用默认栈的问题 |
| **AI** | `packages/ai_agent`（消息总线 / 工具循环 / 技能体系 / cron） | 新增 UI 通道接入消息总线，使 agent 的每一次回复自动镜像上屏；新增 PTT 与唤醒两条语音入口；工具白名单裁剪 37 → 9 |
| **多媒体** | AUDCODEC（音频子系统） | **实现全树首个可用的 SF32LB52 录音驱动**，打通 ADC 采集 → 编码 → 上行全链路 |

**对 openvela 的改进建议**（均已形成上游 PR）：

1. `packages/ai_agent`：`vela_tls` 请求体超过 16 KB 必然失败（单次写上限）；`skill_loader` 描述解析为死代码导致全部内置技能描述为空；`ws_server` pong 无锁写与分帧发送导致帧交错。
2. `vendor/sifli`：AUDCODEC HAL 有 5 处缺陷（`ADC_ENABLE` 调用点被注释、`Refgen`/`Volume` 无头文件声明、`Config_ADCPath` 实现被 `#if 0` 屏蔽），本作品以显式原型声明绕过，**建议补入 HAL 头文件**。
3. `apps/pppd`：该实现按「拨号 modem」编写，直连串口场景下会因 `AHDLC_TX_OFFLINE` 计数与 `ip_no_data_time` 误判链路离线，进而向 PPP 字节流写入 `+++`/`ATE1` **自毁正常链路**。

#### 关键机制设计

**① 消息总线镜像上屏**：在 agent 的出站分发处统一镜像一份到 LVGL 通道，一处覆盖所有来源（语音 / WebSocket / cron 主动推送）。为避免 cron 唤醒时调度器自己写的提示词被误显示成"用户说的话"，为消息结构增加了 `internal` 标志。

**② 工具白名单**：在 `tool_registry` 增加 `s_exposed_tools[]` 白名单并在构建工具 JSON 时过滤，请求体从 15481 字节降到 7347 字节——这在 12.7 KB/s 的链路上是数量级的差异。

**③ 时钟偏移而非改时钟**：板载 RTC 上电即为 2036 年，而时钟校验只检查下界（`now > 2025-01-01`），**错到未来反而被永久信任**。直接 `settimeofday` 会使已挂载的定时器全部错乱并导致设备卡死，故改为记录 `s_time_offset` 偏移量，报时与系统提示词均叠加该偏移，**系统时钟一个字节都不动**。

#### 数据流与关键流程

```
用户说话
   ↓
[设备] AUDCODEC ADC 采集 (5801 Hz)
   ↓ μ-law 编码，1 字节/样本
[设备] WS 二进制帧持续上行（约 5.8 KB/s）
   ↓ PPP over 串口
[PC] 串口桥 → PPP 解封装 → 语音桥
   ↓ 能量 VAD 切句
[PC] 唤醒词门控（未唤醒则丢弃，防环境噪声误触发）
   ↓
[PC] sherpa-onnx Paraformer 离线识别
   ↓ 命令路由（规则表）
[PC] 经 LLM 代理转发至 DeepSeek，执行工具循环
   ↓ 回传命令
[设备] agent 执行（shell / cron / 屏幕输出）
   ↓
[设备] 结果镜像至 LVGL 通道 → 中文显示在圆屏
```

#### 硬件设计与适配

| 项 | 内容 |
|---|---|
| 开发板 | 立创·黄山派 SF32LB52-LCHSPI-ULP（Cortex-M33 + 8MB PSRAM + 16MB Flash） |
| 板载外设 | AMOLED 触摸圆屏、MEMS 麦克风、功放喇叭、六轴 IMU、光感、蓝牙 5.3 |
| 外接模块 | 无。仅一根 USB 数据线，同时承载控制台、烧录与 PPP 网络链路 |
| **是否完成全新硬件平台适配或驱动开发** | **是** |

**新增驱动：SF32LB52 AUDCODEC ADC 录音驱动**（openvela 全树首个可用实现）

适配难点与解决方案：

| 难点 | 现象 | 解决 |
|---|---|---|
| `ADC_ENABLE` 调用点被注释 | 采集启动后无任何数据 | 恢复调用并置于正确的初始化时序中 |
| `HAL_AUCODEC_Refgen_Init` 与 `Config_ADCPath_Volume` 无声明 | 编译失败，且**无法直接调用** | 驱动内以显式原型声明，并在上游 PR 中建议补入 HAL 头文件 |
| `Config_ADCPath` 实现被 `#if 0` 屏蔽 | 通道配置静默失效 | 绕开该分支，直接走 HAL 的音量/通道接口 |
| ADC 转换无参考电压 | 采样值恒为 0 | 先初始化 Refgen 再启动 ADC |
| 采样率标定 | 头文件标称值与实际不符 | 实测标定：`clk_div=7 / osr_sel=3` → **5801 Hz**（注意：既有文档记录的 5333 Hz 是错的，偏差 9%） |
| DMA 环套圈丢样 | 音频静默丢失，无任何报错 | 驱动改为**持久读游标**：从上次读到的位置继续，且攒够 1024 样本即返回，使单线程采集-发送也能跟上产出速率 |

#### 应用 / 交互端设计

**界面**：LVGL 圆屏聊天流，用户气泡与设备气泡区分显示，内置 GB2312 字体（6763 汉字，编入固件 +535 KB），全部中文呈现。

**交互入口（两条，互不依赖）**：

| 方式 | 操作 | 是否需要唤醒词 |
|---|---|---|
| **语音唤醒** | 说「你好，openvela」，再说指令；或一口气说完「你好，openvela，现在几点了」 | — |
| **PTT 按钮** | 点一下屏幕蓝色按钮开始录音 → 说话 → 再点一下结束 | 不需要 |

唤醒成功后屏幕会显示「（已唤醒，请说指令）」，8 秒内说出指令即可。

#### 自定义 Skill

本作品沉淀了 **2 个自定义 Skill**（赛事要求 ≥1）：

**① `command-router`——把口语短指令路由到真实工具调用**

- **触发场景**：收到来自语音或 WebSocket 通道的短祈使句（「巡检」「看一下内存」「现在几点了」「在屏幕上显示你好」「取消定时任务」）
- **解决的问题**：本作品是**被说给**的而不是被输入的，语音转写出来就是一句光秃秃的祈使句。不加约束时，模型会**凭自己的记忆回答**——问到「这台设备」的内存时，它会给一个看起来合理的数字并显示在屏幕上。**编造的数字和真实的数字在屏幕上长得一模一样**，这是本场景下最糟的失败模式。
- **做法**：技能正文给出一张路由表（用户说法 → 调用的工具 → 后续动作），并规定「设备事实只能来自工具返回，绝不来自记忆」「一轮只调一个工具，看过返回再决定下一个」「回复渲染在手表屏幕上，一到两行、无表格、无 Markdown」。

**② `device-guardian`——设备巡检**

- **触发场景**：被定时任务（`wake_agent=true` 的 cron）唤醒时，或用户询问设备健康状态时
- **做法**：按需调用 `run_shell` 执行 `free` / `ps` / `df` / `uptime`，按固定格式输出 3~6 条中文简报（运行时长 / 内存 / 网络 / 存储 / 异常与建议），并内置判据：**空闲堆低于 1 MB 为危急、低于 2 MB 为警告**；文件系统占用超过 85% 为警告；无接口持有 IPv4 地址即网络中断。

**⚠️ 已知平台缺陷（openvela / NuttX 内核，非本作品代码）**

设备会**间歇性挂死**：屏幕冻结、ping 不通。定位到如下断言：

```
dump_assert_info: Assertion failed at
  ../../nuttx/sched/semaphore/sem_waitirq.c:137
DEBUGASSERT(mutex || atomic_read(NXSEM_COUNT(sem)) < 0);
```

即信号量「超时 vs post」竞态。触发点在 TCP 接收路径：

```
nxsem_tickwait → net_sem_timedwait2 → conn_dev_sem_timedwait
             → tcp_recvfrom_one → psock_tcp_recvfrom → vela_http_post_json
```

每次 LLM HTTP 请求都会经过该路径，因此**崩溃随机且频繁**（实测 4~30 轮 agent 回合不等）。

**已排除的假设**：不是栈溢出——开启 `CONFIG_STACK_CANARIES` 后**未触发**，且将 LVGL 线程栈 16→32 KB、`mic_stream` 4→8 KB、cron 8→16 KB 均无改善；也不是麦克风或音频链路（纯文本 agent 回合即可复现）。

**兜底方案**：`clean_rebuild.sh` 一条命令约 1 分钟恢复（无需插拔）。该缺陷已作为平台问题记录，建议上游修复。

> 附带产出：为定位该问题而开启的栈金丝雀，虽然未能命中崩溃，却暴露出它本身的性能代价——ulaw 编码为**每采样一次函数调用**，金丝雀使音频交付率从 95% 跌至 54%。该配置已移除，音频交付率恢复至 95%。**这条实测数据同时说明了「交付速率 == 采样率」这一自检标准的价值：它捕捉到了一次会让语音识别静默劣化 40% 的性能回归。**

**AI 在各环节的作用**：

| 环节 | AI 的作用 |
|---|---|
| **需求拆解 / 方案设计** | 对比「设备直连 LLM vs PC 代理」「无网卡下的可行联网路径」「16 kHz PCM vs 8 kHz vs 5.8 kHz μ-law」，逐项给出带宽与可行性测算，最终定下 PPP-over-串口 + PC 代理架构 |
| **编码** | AUDCODEC 录音驱动、LVGL 中文字体与聊天 UI、PPP/WS 网络层、PC 端 36 个工具脚本，几乎全部由 AI 生成初稿后人工验证修改 |
| **调试（价值最高）** | 根因定位。例如把「设备跑几分钟必死」逐层缩小到 pppd 内部的拨号时代自毁逻辑；把「音频跑 6 秒后停发」定位到驱动 read 语义导致的 DMA 套圈；把「设备偶发挂死」定位到 NuttX 内核信号量竞态的具体断言 |
| **文档** | 本报告、README、部署说明、上游 PR 描述均由 AI 起草后人工定稿 |

**遇到的典型问题与解决方式**：

1. **AI 的自信错误需要实验证伪**：定位音频丢样时，曾假设是线程栈不足并据此加大各线程栈，观察到「4 轮→15 轮」的改善便一度认为成立；后续用栈金丝雀做对照实验，**证明该判断是错的**（金丝雀从未触发，加大栈也无改善），那点改善只是波动。**教训：性能与稳定性问题上，单次观察到的改善不足以作为因果证据。**
2. **环境噪声会被识别器「自信地」转写成流利中文**：`然后我觉得你`、`中年卫地` 等与真话在日志上无法区分。解决方式是要求命令词命中，未命中即丢弃；再叠加唤醒词门控。
3. **静默失败最难查**：识别失败、DMA 丢样、音频停发等现象都不报错。为此在关键路径上补齐了显式日志与自检脚本（`wake_test.py`、`measure_rate.sh`、`soak.sh`）。

### 3.7 总结与展望

#### 成果总结

1. **端到端闭环跑通并实机验证**：唤醒 → 识别 → 理解 → 设备执行 → 中文上屏，全部在真实硬件上完成。
2. **主动能力落地**：定时唤醒 agent 本体执行完整工具链并主动汇报，非「定时弹通知」。
3. **零网卡设备的完整联网方案**：一根 USB 线承载控制台、烧录与网络，带宽预算 12.7 KB/s 内跑通音频 + 控制 + 数据。
4. **为平台补齐能力**：实现 openvela 全树首个可用 AUDCODEC 录音驱动；沉淀 2 个自定义 Skill。
5. **回馈上游**：定位 23 处平台缺陷与 5 处配置问题，16 处已含在三个补丁内并提交 PR，其余已在 PR 描述中列出供组委会参考。

#### 应用前景与商业价值

**目标受众**：本作品面向的是「**需要一台设备替人盯着、并在异常时主动开口**」的场景。

| 场景 | 用户 | 价值 |
|---|---|---|
| **无人值守设备自检** | 工业现场的巡检/运维人员 | 设备按计划自检并在异常时主动汇报，替代人工定时巡检 |
| **可穿戴 AI 助手** | 需要解放双手的一线作业人员 | 喊一声即可查询设备状态，不必掏出手机或连接电脑 |
| **展会 / 教学演示** | 展馆、高校 | 断网环境下仍可完整演示，不受场馆网络质量影响 |

**商业模式与规模化潜力**：

- **短期**：作为 openvela 平台的参考实现与开发者套件，降低「语音 + 主动任务」类应用的开发门槛。
- **中期**：端云协同架构可直接产品化——设备侧保持轻量（本作品设备侧算力占用接近于零），推理成本集中在云端，**单设备成本可控**；断网降级能力使其在网络不可靠的工业现场同样可用。
- **长期**：本作品沉淀的 `command-router` 模式（把口语指令路由到设备真实工具调用，而非让模型凭记忆作答）是**端侧 AI 助手可信度的关键**，可复用至任何「LLM 需要操作真实设备」的场景。

#### 不足与未来工作

1. **平台稳定性依赖上游修复**：NuttX 信号量竞态会导致设备间歇性挂死，当前以自动重建脚本兜底，**根本修复需在内核层完成**。
2. **语音识别受限于采样带宽**：5801 Hz 采样（奈奎斯特上限 2.9 kHz）使英文专有名词的识别不稳定，唤醒词因此采用「锚点 + 拉丁字母」的宽松匹配。后续可评估提升采样率（需在带宽预算内重新分配）。
3. **LLM 依赖 PC 代理**：属演示架构。产品化应内置 TLS 修复或改用端侧小模型。
4. **主动任务目前是定时型**：阈值型 / 事件型（如电压异常告警）已在工具层预留接口，尚未接入真实传感器。
5. **未做低功耗优化**：当前为常供电演示形态，可穿戴产品化需引入休眠与唤醒管理。
