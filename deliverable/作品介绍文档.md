## 一、作品概述

一个跑在黄山派（SiFli SF32LB52）开发板上的**端云协同语音 Agent**：

对着板子说话，设备负责采集与执行，PC 负责理解与推理，屏幕用中文回话；
同时它按计划**主动巡检设备状态**，不需要任何人开口。

一句话卖点：**在一块没有 WiFi、没有操作系统的"裸板"上，
用一根 USB 线实现了「语音进、执行出、中文上屏、主动汇报」的完整 Agent 闭环。**

## 二、目标用户与使用场景

| 用户 | 场景 |
|---|---|
| 嵌入式开发者 | 对着开发板口述指令完成巡检（"看一下设备内存"），不必连串口敲命令 |
| 智能终端用户（手表/桌面设备） | 设备无人值守时按计划自检并主动汇报异常 |
| 展会/教学演示 | 无网络环境下依然可完整演示（本地 ASR + 可切 mock LLM） |

**痛点**：现有嵌入式 AI 演示普遍是"连着电脑敲命令"或"必须联网才有反应"。
本作品解放了两端——设备端无按键启动、语音是唯一入口；网络端断网可降级，演示不中断。

## 三、用户故事（4 个）

### 故事 1：语音下命令
> 我对着板子按住按键说"**现在几点了**"，松手后屏幕立刻显示当前时间；说"**看一下设备的内存**"，
> 屏幕显示内存占用。全程不需要电脑、不需要键盘。

### 故事 2：主动巡检（核心差异化）
> 我说"**请每两分钟巡检一次设备**"。之后我什么都不做，每两分钟屏幕上自动出现一条巡检结果
> （内存、任务数、链路状态），PC 端同步收到。设备无人值守时也在工作。

### 故事 3：断网可用
> 展会上网络断了。设备与 PC 的链路不受影响（走的是本地 PPP 链路而非互联网），
> LLM 通道自动降级为本地 mock 剧本，语音识别仍在设备侧链路本地完成，
> **演示不中断**。

### 故事 4：屏幕即回执
> 每一次语音指令、每一次巡检、每一次错误，都会在屏幕聊天流里以中文气泡显示，
> 不用连串口看日志就知道设备在做什么。

## 五、技术实现

### 5.1 系统架构

```
┌─────────────────────── 黄山派 SF32LB52 ───────────────────────┐
│  MEMS MIC → AUDCODEC ADC → μ-law 编码 → WS 二进制帧           │
│  LVGL 聊天界面（中文）  ← 消息总线 ←  agent 核心（工具循环）   │
│  主动任务（cron）        →  到点自动巡检 → 上屏 + 上行         │
└──────────────────────────┬───────────────────────────────────┘
                           │ PPP over 串口（实测 12.7 KB/s）
┌──────────────────────────┴───────────────────────────────────┐
│  PC（云侧）：PPP 服务端 + NAT + 串口桥                         │
│   语音桥：VAD → 离线 ASR（Paraformer）→ 命令路由               │
│   LLM 代理：设备明文 HTTP → HTTPS（DeepSeek 等）/ 本地 mock    │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 使用的 ai_agent 核心能力

| 能力 | 本作品的使用方式 |
|---|---|
| **消息总线** | 新增 UI 通道接入：agent 的每一次回复镜像到 LVGL 屏幕；`internal` 标志区分系统事件 |
| **主动任务（cron）** | "每两分钟巡检一次"即注册一条 cron 任务，到点唤醒 agent 执行工具链 |
| **Tool 调用** | 时间查询、内存/任务读取、定时任务管理等工具，由 LLM 自主选择调用 |
| **Router 意图路由** | 语音转写 → 命令路由分流（控制类命令 vs 对话类请求） |
| **多渠道** | 语音（WS）、文本（WS）、REST、屏幕四条通道并存 |
| **Skill 体系** | 12 个内置技能随固件生效；修复了技能描述解析缺陷（上游 A23） |

### 5.3 三个关键技术决策

1. **码率预算驱动的音频设计**：实测串口链路只有 ~12.7 KB/s（CH340 + USB/IP 的物理上限），
   16 kHz×16 bit 需要 32 KB/s 根本传不动。改用 **G.711 μ-law 单字节/样本 @5801 Hz
   ≈ 8 KB/s**，再把 ×2.76 重采样到 16 kHz 喂离线 ASR——**无损、可识别、余量充足**。
2. **无头 + 无竞态启动**：`ai_agent < /dev/null`（读 EOF 即退出 CLI 线程）+ `pppd` 前台运行
   （NSH 阻塞在 waitpid，不再与控制台争抢），一条命令完成启动，无需人工交互。
3. **PC 代理 LLM**：设备端 TLS 路径在 16 KB 以上不可靠（上游 A20），改为设备走明文 HTTP
   到 PC，由 PC 代理转 HTTPS——顺带获得了"断网切 mock"的演示能力，**真实 API Key 从不进设备**。

### 5.4 上游贡献（附带产出）

开发过程中定位并修复了 **23 处 openvela 平台缺陷**（A1–A23）与 **5 处配置问题**（B1–B5），
其中 5 处已包含在本作品补丁中，其余按赛事要求单独向公共仓提 PR。
典型如：`vela_tls` 超过 16 KB 必失败、技能描述解析死代码致 12 个内置技能全部失效、
pppd 在直连串口下被误判离线后自我拆链等。

## 六、实测数据

| 指标 | 实测值 |
|---|---|
| 音频上行码率 | 8 KB/s（μ-law 8 bit @5801 Hz） |
| 串口链路有效带宽 | ~12.7 KB/s（PPP 开销 17%，正常） |
| 链路稳定性 | 连续 6 分钟 0 掉线（修复前 30–60 秒必死） |
| 语音识别 | 设备侧 5801 Hz 采集 → PC 重采样 16 kHz → 离线 Paraformer |
| 中文显示 | GB2312 全覆盖，固件增量约 +535 KB |
| 端到端时延 | 按下说话 → 松手 → 屏幕出结果：秒级 |

## 八、局限与下一步

- LLM 通道依赖 PC 代理（属演示架构；产品化应内置 TLS 修复或走端侧小模型）

- 快应用/手表生态对接（在本板无 BT 语音通路的约束下暂缓）
